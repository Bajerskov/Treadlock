# Targeting the AMD BC-250

The BC-250 is an ASRock Rack mining board built around a cut-down PlayStation 5
APU. It is the primary target for Treadlock, so its quirks shape the engine.

## Specifications

| | |
| --- | --- |
| APU | Cut-down PS5 part ("Oberon" / Cyan Skillfish) |
| CPU | 6 of 8 Zen 2 cores active at ~3.5 GHz; the other two are not fused off and can be unlocked |
| GPU | RDNA 2, 24 CUs, `gfx1013`, 1500 MHz base and up to 2000 MHz stock |
| GPU class | Between an RX 6600 and an RX 6600 XT for rasterisation; entry-level for ray tracing |
| Memory | 16 GB GDDR6, 256-bit, 14 Gbps, ~448 GB/s, shared between CPU and GPU |
| Storage | 1x M.2 2280, PCIe 2.0 x2, so about 1 GB/s |
| Display | 1x DisplayPort 1.4, no HDMI |
| Power | 220 W TDP, measured up to 235 W |
| OS | Linux only; there are no Windows drivers |

## What this means for the engine

**Bandwidth is not the constraint.** ~448 GB/s is console-class and far beyond
a typical APU. Techniques that would be reckless on an integrated GPU - a fat
G-buffer, high-resolution render targets - are affordable here. The real limits
are the 24 CUs and ray tracing throughput.

**Ray tracing must be budgeted like an RX 6600.** Hardware RT is present, but
entry-level. Full-resolution ray-traced reflections will not hold 60 fps. The
plan is a hybrid: screen-space reflections as the base layer, with rays traced
only where screen space fails - off-screen geometry and grazing angles - at
half resolution and temporally denoised.

Because `gfx1013` sits in the `gfx101x` ISA family while being marketed as
RDNA 2, driver support for ray queries is worth confirming on the actual board
rather than assuming. The engine therefore probes `VK_KHR_ray_query` at startup
and reports what it found, and will fall back to screen-space-only reflections
if it is missing. Run the game and check the first line of output.

**No video decode at all.** The VCN block is present but its firmware is
blocked by Sony, so there is no hardware encode or decode. Consequences:

- No prerendered video, ever. All cutscenes, menus and transitions must be
  rendered in-engine.
- Capturing or streaming gameplay will be CPU-bound.

**Storage is slow.** PCIe 2.0 x2 caps the M.2 slot at roughly 1 GB/s. A
procedurally generated world is a good architectural fit here, because it
largely removes asset streaming from the critical path. Keep generation on the
CPU cores rather than loading from disk.

**VRAM is a BIOS setting.** The 16 GB is split between CPU and GPU in firmware,
with 512 MB dynamic recommended. The engine must not assume a fixed VRAM
budget; allocate against what the driver actually reports.

**Vulkan 1.3 is a safe baseline.** Mesa 25.3+ reports Vulkan 1.4 on this board,
so dynamic rendering and synchronization2 - both used here - are available
without extension juggling.

## Practical setup notes

- IOMMU is broken on this board and must be disabled in BIOS, or you get black
  screens and crashes. GPU passthrough is therefore not possible.
- The stock heatsink is passive and designed for rack airflow. Active cooling
  is required for sustained gameplay.
- Secure Boot and TPM are not supported.

## Portability

Nothing above is load-bearing for correctness. The renderer targets Vulkan 1.3
and detects ray query support at runtime, so the game should run on any
reasonably modern GPU. The BC-250 sets the performance budget, not the API
floor.
